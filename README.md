# ms-account-reservation

## UPG-9. Устранение N + 1 при работе с клиентами и счетами

### Исходная проблема

При формировании ответов API маппер обращался к ленивым связям
`Client.accounts` и `Account.status`.

При поиске клиентов это приводило к дополнительным запросам
для каждого клиента страницы — проблеме N + 1.

### Получение клиента по ID

Метод `ClientRepository.findDetailsByIdAndStatusNot` использует:

- `LEFT JOIN FETCH c.accounts` — загрузку счетов вместе с клиентом;
- `LEFT JOIN FETCH a.status` — загрузку статусов счетов в том же запросе.

Клиенты без счетов сохраняются в результате.
Клиенты со статусом `DELETED` исключаются.

Статус клиента хранится непосредственно в таблице `client`,
поэтому отдельный запрос для него не требуется.

Маппер продолжает обращаться к счетам и их статусам,
но необходимые связи уже загружены.

Получение клиента выполняется за один SQL-запрос.

### Поиск клиентов с пагинацией

Поиск реализован в default-методе
`ClientRepository.searchWithActiveAccountsCount`.

Условия фильтрации остаются в `ClientSpecifications`:

- исключение клиентов с указанным статусом;
- поиск по части фамилии без учёта регистра;
- фильтрация по `mdmId`.

Страница клиентов загружается через
`JpaSpecificationExecutor.findAll(specification, pageable)`.

Построением основного запроса, применением пагинации и подсчётом
общего количества клиентов занимается Spring Data JPA.
Ручная реализация репозитория с `EntityManager` удалена.

После получения страницы собираются ID её клиентов.
Метод `countActiveAccountsByClientIds` одним запросом получает
количество активных счетов для всех этих клиентов.

Запрос использует:

- `IN :clientIds` — ограничение клиентами текущей страницы;
- фильтрацию по активным статусам счетов;
- `COUNT` и `GROUP BY` — подсчёт счетов каждого клиента.

Активными считаются счета в статусах
`NEW`, `IN_CREATION`, `CREATED`.

Результаты объединяются в `ClientSearchProjection`.
Если для клиента нет активных счетов, используется значение `0`.

Коллекция `Client.accounts` при поиске не загружается:
маппер получает уже рассчитанное количество счетов.

Сохранены:

- формат REST-ответов;
- фильтрация клиентов;
- сортировка по фамилии, имени и ID;
- метаданные страницы;
- существующие сервис и маппер.

Пагинация выполняется на стороне БД, без fetch join коллекции.

### Количество SQL-запросов

| Сценарий | Количество запросов |
|---|---:|
| Получение клиента по ID со счетами и их статусами | 1 |
| Непустая страница поиска с выполнением COUNT | 3 |

Для страницы поиска выполняются:

1. Запрос клиентов текущей страницы.
2. Запрос общего количества подходящих клиентов.
3. Общий запрос количества активных счетов клиентов страницы.

Отдельных запросов для каждого клиента нет.
Количество запросов не растёт с количеством клиентов страницы.

Если Spring Data может определить общее количество клиентов
без отдельного COUNT, запросов будет меньше.
Для пустой страницы запрос количества счетов не выполняется.

> Текущая упрощённая реализация устраняет N + 1, но использует
> до трёх запросов вместо исходного ограничения UPG-9 в два запроса.
> Это изменение ограничения требует согласования.

### Тестовые данные

Database Rider загружает их через:

`@DataSet(value = "datasets/client/query-count.yml")`

Программный `DataSetProvider` удалён.

Набор данных содержит:

- удалённого клиента;
- клиента с другой фамилией;
- клиентов для проверки получения по ID;
- счета с активными и неактивными статусами.

Перед тестами и после них выполняется очистка тестовых данных.
Справочник `account_status` и служебные таблицы Liquibase
исключены из очистки.

### Проверки

`ClientQueryCountIntegrationTest` проверяет:

- получение клиента с 0, 1 и 5 счетами за один SQL-запрос;
- поиск страниц размером 1, 5 и 10 клиентов за три SQL-запроса;
- статусы клиентов и счетов;
- количество активных счетов;
- порядок клиентов и метаданные страницы;
- исключение удалённых клиентов и клиентов с другой фамилией.

Количество SQL-запросов измеряется через
`Statistics.getPrepareStatementCount()` после вызова сервиса.

Перед измерением выполняются:

1. `EntityManager.flush()` — выполнение отложенных изменений.
2. `EntityManager.clear()` — очистка persistence context.
3. `Statistics.clear()` — сброс статистики Hibernate.

Подготовка тестовых данных не входит в измеряемый участок.

Тест использует общую конфигурацию интеграционных тестов
с PostgreSQL и Redis в Testcontainers.

Поскольку статистика общая для SessionFactory, класс изолирован
от параллельного выполнения других тестов с помощью `@Isolated`,
а его методы выполняются последовательно.

В тестовом профиле включена настройка
`hibernate.query.fail_on_pagination_over_collection_fetch`,
защищающая от пагинации в памяти при fetch join коллекции.

### SQL-логирование

Для ручной диагностики используется профиль `sql-debug`.

Аргумент запуска приложения:

`--spring.profiles.active=sql-debug`

Профиль включает SQL-логи Hibernate без вывода значений параметров.

```

```

## UPG-10. Интеграция с Apache Kafka: события изменения клиента и идемпотентная обработка

### Назначение

При создании, обновлении и мягком удалении клиента формируются события
`CREATED`, `UPDATED` и `DELETED`.

Публикация реализована через Transactional Outbox: изменение клиента
и сохранение события выполняются в одной транзакции PostgreSQL.
Фоновый отправитель публикует сохранённые события в Kafka.

Consumer обрабатывает события идемпотентно: повторная доставка
не приводит к повторной записи бизнес-результата в аудит.

### Формат события

Ключ Kafka-сообщения — строковое представление `clientId`.
Значение — JSON формата `ClientChangedEvent`:

```json
{
  "eventId": "44444444-4444-4444-4444-444444444444",
  "clientId": "55555555-5555-5555-5555-555555555555",
  "eventType": "CREATED",
  "occurredAt": "2026-11-01T10:00:00Z"
}
```

`eventId` создаётся один раз. Повторная публикация из Outbox сохраняет
исходные идентификатор, тип и время события.

### Топики и подписка

Публикация и чтение настраиваются отдельно:

- `app.kafka.client-events-topic` — топик публикации событий из Outbox.
- `app.kafka.client-consumer-topics` — список входящих топиков consumer.

По умолчанию Outbox публикует в `client-changed.v1`,
а consumer подписан на этот же топик.

Для чтения нескольких топиков задаётся переменная окружения:

```text
KAFKA_CLIENT_CONSUMER_TOPICS=client-changed.v1,client-imported.v1,client-synchronized.v1
```

Список может содержать три или больше топиков. Изменять код listener
при добавлении очередного топика того же формата не требуется.
Настройки применяются при запуске приложения.

Все входящие топики должны содержать `ClientChangedEvent`.
Чтение произвольных форматов событий одним обработчиком не реализовано.

Через `KafkaAdmin.NewTopics` объявляются:

- топик публикации;
- настроенные входящие топики;
- соответствующие DLT-топики с суффиксом `.DLT`.

По умолчанию каждый объявленный топик имеет 3 партиции
и replication factor 1.

### Публикация через Transactional Outbox

Таблица `client_event_outbox` хранит событие и состояние публикации:

- `published_at` — отметка времени успешной публикации;
- `attempts` — количество зафиксированных попыток отправки приложением;
- `next_attempt_at` — время доступности следующей попытки;
- `last_error` — последняя ошибка отправки.

Порядок работы:

1. Сервис сохраняет изменение клиента и событие в одной транзакции.
2. Планировщик вызывает отправитель Outbox.
3. Отправитель выбирает доступное неопубликованное событие.
4. Публикует его через `KafkaTemplate` с ключом `clientId`.
5. После подтверждения Kafka заполняет `published_at`.
6. При ошибке сохраняет информацию о сбое и время следующей попытки.

Каждое выбранное событие обрабатывается в отдельной транзакции.
Для конкурентного выбора используется `FOR UPDATE SKIP LOCKED`.

Более позднее событие клиента не выбирается, пока его предыдущее
событие остаётся неопубликованным.

Повторы Kafka producer и повторные попытки Outbox — разные механизмы.
Поле `attempts` не считает внутренние повторы Kafka producer.

### Планировщик

`@EnableScheduling` вынесена в отдельную `SchedulingConfiguration`
и не зависит от включения Kafka.

При `app.kafka.enabled=false` отключаются прикладные Kafka-компоненты:
listener, отправитель и планировщик Outbox.

Сохранение событий в Outbox при изменении клиента остаётся включённым.
После включения Kafka-компонентов накопленные события доступны для отправки.

### Настройки producer

Используются:

- `acks=all`;
- `retries=10`;
- `enable.idempotence=true`;
- `max.in.flight.requests.per.connection=5`;
- `delivery.timeout.ms=10000`.

Идемпотентность producer не заменяет идемпотентность consumer:
повторная отправка события из Outbox всё равно может создать
повторное сообщение.

### Идемпотентная обработка

Таблица `processed_client_event` хранит обработанные ключи
с составным первичным ключом `(client_id, event_id)`.

В одной транзакции PostgreSQL выполняются:

1. Вставка ключа через `INSERT ... ON CONFLICT DO NOTHING`.
2. Для нового ключа — сохранение записи в `client_event_audit`.
3. Для существующего ключа — пропуск повторного бизнес-действия.

Маркер обработки и аудит фиксируются вместе.
При откате транзакции событие можно обработать повторно.

Хранятся все обработанные ключи, а не только последнее событие клиента.
Повтор старого события после обработки нового также распознаётся.

Идемпотентность действует и между входящими топиками:
событие с одинаковыми `clientId` и `eventId` не создаёт повторный аудит,
даже если пришло из другого топика.

### Consumer и подтверждение offsets

Настройки по умолчанию:

- группа: `ms-account-reservation-client-events-v1`;
- `enable-auto-commit=false`;
- режим подтверждения: `MANUAL_IMMEDIATE`;
- `concurrency=3`;
- `auto-offset-reset=earliest`.

Listener подтверждает сообщение после успешного завершения
транзакции сервиса обработки. Распознанные дубликаты также подтверждаются.

Если обработка завершилась исключением, обычное подтверждение
не выполняется: сообщение передаётся обработчику ошибок.

`auto-offset-reset=earliest` применяется при отсутствии подходящего offset,
а не заставляет consumer перечитывать весь топик при каждом запуске.

### Повторы и DLT

Для повторяемых ошибок по умолчанию выполняются первоначальная попытка
и два повтора с интервалом 1000 мс.

Настройки вынесены в конфигурацию:

- `app.kafka.consumer-retry-count` — количество повторов после первой попытки;
- `app.kafka.consumer-retry-interval-ms` — интервал между повторами;
- `app.kafka.dlt-send-timeout-ms` — настройка ожидания результата отправки в DLT.

После исчерпания повторов сообщение направляется
в DLT своего исходного топика с сохранением номера партиции:

```text
client-changed.v1      → client-changed.v1.DLT
client-imported.v1     → client-imported.v1.DLT
client-synchronized.v1 → client-synchronized.v1.DLT
```

Правило назначения задано явно через `DeadLetterPublishingRecoverer`:
`record.topic() + ".DLT"` и `record.partition()`.

Некорректные события, отклонённые через `InvalidClientEventException`,
направляются в DLT без повторов.

После успешной отправки в DLT подтверждается offset исходного сообщения.
Ошибка отправки в DLT не считается успешным восстановлением.

Автоматическое исправление и повторная отправка сообщений из DLT
не реализованы.

### Гарантии и ограничения

- Публикация допускает повторную доставку: это не глобальная exactly-once-система.
- Если Kafka приняла событие, но отметка Outbox не сохранилась,
  следующая попытка может отправить его повторно.
- Повтор `(clientId, eventId)` не создаёт повторного аудита,
  пока соответствующий ключ хранится в БД.
- Идемпотентность относится к бизнес-действиям внутри той же транзакции PostgreSQL.
  Для внешних побочных эффектов нужна отдельная стратегия.
- Одинаковый ключ обеспечивает выбор одной партиции внутри конкретного топика
  при неизменной схеме партиционирования. Между разными топиками общего порядка нет.
- После переноса события в DLT следующие события клиента могут обрабатываться.
  Успешная бизнес-обработка всех событий строго по порядку не гарантируется.
- Перераспределение партиций или сбои могут приводить к повторной доставке.
- Replication factor 1 предназначен для локального запуска
  и не обеспечивает устойчивость к потере единственного брокера.
- При включённом Kafka admin fail-fast брокер должен быть доступен при запуске.
- Автоматическая очистка Outbox, аудита и ключей идемпотентности не реализована.

### Тестирование

Проверяются:

- совместная фиксация и откат изменения клиента и записи Outbox;
- порядок выбора событий одного клиента;
- повторная публикация с сохранением исходного события;
- атомарность маркера обработки и аудита;
- пропуск повторно доставленного события;
- подтверждение offset после обработки;
- повторные попытки consumer;
- отправка ошибочных событий в DLT;
- продолжение обработки после переноса события в DLT;
- получение событий из каждого настроенного входящего топика;
- выбор DLT соответствующего исходного топика;
- пропуск одинакового события, полученного из разных топиков.

Интеграционные тесты используют PostgreSQL, Redis и Kafka в Testcontainers.
Исходные данные Outbox загружаются через Database Rider и YAML DataSet.

Перед отправкой событий Kafka-тесты ожидают назначения партиций
каждому из трёх consumer, чтобы не начать проверки
во время первоначального формирования группы.

В тесте восстановления Outbox первая ошибка отправки моделируется через spy,
а последующая публикация выполняется в настоящий тестовый брокер.
Физическое отключение брокера и перезапуск приложения этот тест не моделирует.

Для запуска необходим работающий Docker Desktop.

Kafka-интеграционные тесты:

```powershell
.\mvnw.cmd -pl ms-account-reservation-app -am `
    "-Dtest=ClientKafkaIntegrationTest" `
    "-Dsurefire.failIfNoSpecifiedTests=false" `
    "-DargLine=-Xms128m -Xmx768m" `
    test
```

Полная проверка проекта:

```powershell
.\mvnw.cmd clean verify "-DargLine=-Xms128m -Xmx768m"
```

Ограничение heap предназначено для локального запуска
на машине с небольшим объёмом памяти.
