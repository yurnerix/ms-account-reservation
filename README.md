# ms-account-reservation

## UPG-9. Устранение N + 1 при работе с клиентами и счетами

### Исходная проблема

При получении клиента и поиске клиентов маппер обращался к ленивым
связям `Client.accounts` и `Account.status`.

Это приводило к дополнительным SQL-запросам при формировании DTO.
В поиске коллекция счетов загружалась отдельно для каждого клиента,
даже если у него не было счетов.

### Получение клиента по ID

В `ClientRepository` добавлен метод `findDetailsByIdAndStatusNot`.

Запрос использует:

- `LEFT JOIN FETCH c.accounts` — загрузка счетов вместе с клиентом;
- `LEFT JOIN FETCH a.status` — загрузка статусов счетов в том же запросе.

Использование `LEFT JOIN` сохраняет в результате клиентов без счетов.
Клиенты со статусом `DELETED` исключаются.

Статус клиента хранится непосредственно в таблице `client`,
поэтому отдельное объединение для него не требуется.

Маппинг подробного ответа по-прежнему обращается к счетам и их статусам,
но необходимые связи уже загружены.

### Поиск клиентов с пагинацией

В `ClientRepository` добавлен метод `searchWithActiveAccountsCount`.

Основной запрос возвращает проекцию `ClientSearchProjection`:

- сущность клиента;
- количество активных счетов, рассчитанное через `SUM(CASE ...)`.

Активными считаются счета в статусах `NEW`, `IN_CREATION`, `CREATED`.

Отдельный `countQuery` вычисляет общее количество клиентов
для `totalElements` и `totalPages`. Он использует те же фильтры,
но не объединяет таблицы счетов и их статусов.

Сохранены:

- исключение удалённых клиентов;
- поиск по части фамилии без учёта регистра;
- фильтрация по `mdmId`;
- сортировка по фамилии, имени и ID;
- прежний формат REST-ответов.

В поиске используется обычный `JOIN`, а не `JOIN FETCH` коллекции.
Коллекция счетов не загружается: маппер получает уже вычисленное число.

### Количество SQL-запросов

Исходные замеры выполнены на данных с двумя клиентами,
у одного из которых был один счёт.

| Сценарий | До оптимизации | После оптимизации |
|---|---:|---:|
| Клиент по ID со счётом | 3 | 1 |
| Поиск страницы размером 1 | 4 | 2 |
| Поиск страницы размером 2 | 5 | 2 |

Результат после оптимизации подтверждён SQL-логами
и интеграционными тестами.

Для поиска указано количество запросов при выполнении отдельного
`COUNT`. Если Spring Data может определить общее количество
результатов без него, запросов может быть меньше.

### Проверки

`ClientQueryCountIntegrationTest` проверяет:

- получение клиента с 0, 1 и 5 счетами за один SQL-запрос;
- поиск страниц размером 1, 5 и 10 клиентов за два SQL-запроса;
- статусы клиентов и счетов;
- количество активных счетов;
- сортировку и метаданные страницы;
- исключение удалённых клиентов и применение фильтра фамилии.

Перед замером выполняются:

1. `EntityManager.flush()` — запись подготовленных тестовых данных;
2. `EntityManager.clear()` — очистка persistence context;
3. `Statistics.clear()` — сброс статистики подготовки данных.

Количество запросов проверяется через
`Statistics.getPrepareStatementCount()` после вызова сервиса.

Тест наследует общую конфигурацию интеграционных тестов
с PostgreSQL и Redis в Testcontainers.

Поскольку статистика общая для `SessionFactory`, класс изолирован
от параллельного выполнения других тестов с помощью `@Isolated`,
а его методы выполняются последовательно.

В тестовом профиле включена настройка
`hibernate.query.fail_on_pagination_over_collection_fetch`,
защищающая от пагинации в памяти при загрузке коллекций через fetch join.

### SQL-логирование

Для ручной диагностики используется профиль `sql-debug`.

Аргумент запуска приложения:

`--spring.profiles.active=sql-debug`

Профиль включает SQL-логи Hibernate без вывода значений параметров.

### Запуск тестов

Для интеграционных тестов необходим работающий Docker.

Проверка количества SQL-запросов из корня проекта:

`.\mvnw.cmd -pl ms-account-reservation-app -am "-Dtest=ClientQueryCountIntegrationTest" "-Dsurefire.failIfNoSpecifiedTests=false" test`

Полный прогон тестов:

`.\mvnw.cmd clean test`
